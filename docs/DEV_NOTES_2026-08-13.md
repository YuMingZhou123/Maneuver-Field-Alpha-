# 2026-08-13 开发讨论记录

这份文档记录今天下午围绕 Maneuver Field Alpha / Maneuver Field Alpha 讨论过的游戏开发方向、流程和工程判断。它不是最终方案，而是后续开发时用来回顾决策依据的项目笔记。

## 1. 项目定位

当前项目先作为 Unity 手游原型开发，名称暂定为 Maneuver Field Alpha / Maneuver Field Alpha。正式名称可以等玩法、美术和世界观更明确后再调整。

项目方向：

- 原创机甲都市竞技手游
- 移动端优先
- 先做单机 Demo 验证手感
- 后续再考虑 AI、联机、账号、商城和正式运营系统

需要注意：公开表达时不建议使用“复刻”作为正式描述，更适合表述为“受机甲都市竞技类玩法启发的原创移动端游戏原型”。

## 2. 引擎选择

讨论过 Unity、Cocos、Godot 的区别后，当前选择 Unity。

选择 Unity 的原因：

- 更适合 3D 手游、动作、射击和机甲玩法
- 移动端打包、动画、摄像机、物理和 UI 生态成熟
- 插件、教程和团队协作资源更多
- 后续做 Android / iOS 真机测试更稳

Cocos 更适合 2D、轻量手游或小游戏；Godot 开源轻量，但复杂 3D 手游和商业移动端生态相对弱一些。对于本项目，Unity 更合适。

## 3. Unity 和代码编辑器的分工

游戏代码一般不是直接在 Unity 编辑器里大量编写，而是在 Visual Studio、Rider 或 VS Code 中写 C# 脚本。

分工方式：

- Unity：搭场景、放模型、挂组件、调 Inspector 参数、做 Prefab、配置 UI、运行测试
- Visual Studio / Rider / VS Code：编写 C# 脚本，例如角色控制、摄像机、武器、技能和 UI 逻辑

典型流程：

1. 在 Unity 中创建场景对象或 Prefab。
2. 创建 C# 脚本。
3. 用 Visual Studio 打开脚本并编写逻辑。
4. 保存代码。
5. 回到 Unity，等待自动编译。
6. 把脚本挂到对象上并调参数。
7. 点击 Play 或打包到手机测试。

新手阶段建议直接使用 Unity 推荐的 Visual Studio 2022。

## 4. 游戏开发整体流程

推荐不要一开始做完整游戏，而是按阶段推进。

### 阶段 1：前期定位

明确项目边界：

- 是 3D 机甲动作手游，还是偏射击竞技
- 核心爽点是高速移动、机甲感、城市空间、射击命中还是技能对抗
- 第一版做什么，不做什么

当前建议：先做“单机训练场手感验证”。

### 阶段 2：技术准备

- 选择 Unity LTS 版本
- 创建 3D URP 工程
- 平台先选 Android
- 横屏优先
- 建立测试场景 PrototypeScene
- 做一次空项目 Android 打包

重点是尽早确认手机能跑起来。

### 阶段 3：核心操作原型

先做一个占位机甲：

- 左侧虚拟摇杆移动
- 右侧拖拽控制镜头
- 第三人称摄像机跟随
- 机甲转向
- 跳跃或上升
- 冲刺 / 推进
- 简单能量条或冷却

判断标准是手机上操作是否舒服、是否晕、是否卡顿。

### 阶段 4：基础战斗原型

- 一把基础远程武器
- 射线或简单弹道
- 训练靶
- 命中反馈
- 伤害数字
- 开火冷却
- 冲刺技能和射击配合

先验证最小战斗闭环，不急着做大量技能。

### 阶段 5：灰盒地图

用方块搭一张小型城市测试地图：

- 街道
- 楼体
- 掩体
- 高低差
- 屋顶
- 坡道或跳台
- 多条移动路线

目标不是好看，而是验证移动、射击和冲刺在城市空间里是否成立。

### 阶段 6：内容扩展

在核心闭环成立后，再逐步加入：

- 第二台机甲
- 第二把武器
- 第二个技能
- 简单 AI 敌人
- 基础生命值系统
- 简单胜负条件
- UI、音效和基础特效

### 阶段 7：联机或模式验证

如果未来做多人竞技，推荐顺序是：

1. 单机手感稳定
2. 加本地 AI 或训练目标
3. 小规模联网验证，例如 1v1 或 2v2
4. 再考虑匹配、房间、排行、大地图和多人模式

不要一开始就做“大逃杀 + 多人联机”，因为联网同步、延迟、服务器成本和反作弊都很重。

### 阶段 8：正式化和打磨

最后再进入正式游戏内容：

- 正式角色设计
- 正式美术风格
- 世界观
- UI 视觉
- 音效音乐
- 新手引导
- 数值平衡
- 性能优化
- 测试包
- 宣传素材
- 正式命名

## 5. 数据库是否需要

前期不需要数据库。当前阶段应先做 Unity 单机 Demo。

前期可以使用：

- ScriptableObject 管理机甲、武器、技能配置
- PlayerPrefs 保存简单本地设置
- 本地 JSON 保存测试数据

什么时候需要数据库：

- 玩家账号
- 背包和皮肤拥有关系
- 商城和支付
- 战绩和排行榜
- 多人匹配
- 邮件、活动和运营数据

推荐演进路线：

1. Demo 期：Unity 单机，无后端
2. 小测试期：Unity + 单体 Game API + 数据库
3. 多人验证期：Unity + Game API + Battle Server + Redis
4. 正式运营期：按业务压力拆服务

## 6. 工程架构原则

项目后期要从 Demo 扩展为正式游戏，所以代码结构要谨慎，但不宜一开始过度设计。

推荐原则：

- 模块边界清晰
- 配置数据化
- UI 不直接控制战斗逻辑
- 输入层和玩法层分离
- 机甲、武器、技能尽量通过配置扩展
- 后端边界先预留，但不要早期就做完整微服务

建议模块：

- Core：启动、上下文、服务注册
- Input：手机触控、键鼠调试、未来手柄/AI 输入
- Player：机甲移动、状态、控制入口
- Camera：第三人称跟随和视角控制
- Combat：武器、命中、伤害
- Skills：冲刺、技能冷却、能量消耗
- Config：ScriptableObject 配置
- UI：HUD、按钮、血条、技能冷却显示
- Data：本地存档，未来扩展远程数据

关键判断：Demo 可以写得快，但核心模块边界不能乱。

## 7. 网络游戏后端框架

网络游戏后端可以拆服务，但不建议一开始就上完整微服务。

成熟网络游戏常见模块：

- Auth Service：登录、Token、账号验证
- Player Service：玩家资料、等级、昵称
- Inventory Service：背包、皮肤、机甲拥有状态
- Loadout Service：当前装备的机甲、武器、皮肤
- Shop Service：商城商品、价格、购买记录
- Payment Service：支付订单和平台回调
- Matchmaking Service：匹配和房间分配
- Battle Server：实时战斗、同步、命中、结算
- Mail Service：邮件、补偿、奖励
- Ranking Service：排行榜、战绩
- Config Service：配置、活动、资源版本
- Analytics / Log：日志、留存、付费和异常分析

本项目更适合的路线是先做单体后端，等业务复杂后再拆服务。

## 8. 客户端资源和后端服务的关系

模型、材质、场景、特效、音效这些资源本体一般属于客户端或资源包，不属于微服务。

例如：

- 机甲模型在 Unity 客户端
- 皮肤材质在 Unity 客户端或 Addressables / AssetBundle
- 场景地图在 Unity 客户端或资源包
- 后端记录玩家是否拥有某个皮肤
- 后端记录玩家当前装备哪个皮肤
- 后端返回 skinId、mechaId、weaponId
- 客户端根据这些 ID 加载对应资源并显示

后端控制的是“权限和选择”，客户端负责“加载和表现”。

典型装备皮肤流程：

1. 玩家点击装备皮肤。
2. 客户端发送 skinId 给后端。
3. 后端检查玩家是否拥有该皮肤。
4. 后端保存当前装备状态。
5. 后端返回 selectedSkinId。
6. 客户端根据 selectedSkinId 找到 SkinConfig。
7. 客户端加载对应材质、模型、图标或特效。
8. Unity 把资源应用到机甲对象上。

多人战斗中，服务器通常同步外观 ID，而不是传输模型文件。

## 9. 当前下一步建议

短期优先顺序：

1. 用 Unity Hub 在仓库目录创建 Unity 3D URP 工程。
2. 建立 PrototypeScene。
3. 先做 IInputProvider、MobileInputController、MechaMotor、MechaController。
4. 加 ThirdPersonCameraController。
5. 加 WeaponController、Damageable 和训练靶。
6. 加 BoostSkill。
7. 用灰盒搭第一张城市测试地图。
8. 尽早 Android 真机测试。

不要急着做数据库、商城、账号、正式联机和完整美术。这些应该在核心手感成立后再推进。
